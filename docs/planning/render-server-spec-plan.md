# Plan: server-generated render code (close the viewer-RCE hole)

**Status:** IN PROGRESS (2026-07-13). Socle + first component (table1) DONE:
- `POST /execute/render` added (viewer-gated, `{kind, spec}`, no free code); `/execute`
  now REFUSES `purpose="render"` — the hole is closed for any migrated kind.
- Server render registry: `app/services/execution/render/` (`__init__.py` + `table1.py`,
  `_TABLE1_PY` ported verbatim from the frontend builder).
- Frontend: `renderOnServer()` helper; Table1Component sends `{kind:'table1', spec}`;
  `table1-server.ts` now exports `buildTable1Spec` (Python removed).
- Tests: `test_render.py` (spec validation + JSON-embedding), render endpoint tests +
  updated security-gating test in `test_execution.py` (viewer render OK via /render,
  free code under purpose=render → 400).

REMAINING: migrate the other 8 builders (correlation-matrix, map, kaplan-meier, sankey,
key-indicator, regression, plot-builder, statistical-tests) the same way; each needs its
`_XXX_PY` ported to `render/<kind>.py` + a spec validator + registry entry + component
switched to `renderOnServer` + a parity/endpoint test. Until a kind is migrated its
component still calls the removed `purpose='render'` path and will 400 — so migrate +
switch each component in the same change. Once all 9 are done, drop `render` from the
ExecuteRequest.purpose enum entirely.

## Problem

`POST /execute` runs the client-supplied `code` verbatim. For `purpose="render"` the
gate is only `project-summary:read` (viewer). The design *assumes* render code is
"generated by a built-in component, not typed by a user" — but the backend never
verifies that, so a viewer can send `purpose="render"` with arbitrary Python/R and
get server-side code execution in the project's working dir (files + DB connections).
Server-mode only; not in the shipping WASM build. See REVIEW-LOG.md 2026-07-12 (🔴).

## Chosen approach

For `purpose="render"`, the client no longer sends `code`. It sends a **structured
spec** (analysis kind + column names + options). The **server** owns the static
Python program per analysis and only injects the validated spec. Free-form `code`
is **refused** for render. A viewer can then only run the aggregations the server
knows how to build.

## Why this is tractable (the key finding)

The 9 analysis components already delegate their Python to isolated
`*-server.ts` builder files (1823 lines total). Every builder has the same shape:

```ts
export function buildXxxCode(columns, ...config): string {
  const spec = { /* column NAMES + a few options */ }
  return `${_XXX_PY}\n_linkr_print_xxx(dataset, _json.loads(${JSON.stringify(JSON.stringify(spec))}))\n`
}
const _XXX_PY = String.raw`  ... static python, ZERO interpolation ...`
```

So the only per-request variable is the small `spec` object. `_XXX_PY` is already a
static, self-contained program. The backend already generates the dataset-injection
preamble the same way (`app/services/execution/injection.py` — `python_preamble_from`
embeds path/columns/filters via `json.dumps`, data-as-data). We extend that exact
pattern: move each `_XXX_PY` block server-side, keep sending only the spec.

The 9 builders (size = migration weight):
`correlation-matrix-server.ts` (73), `map-server.ts` (94), `table1-server.ts` (111),
`kaplan-meier-server.ts` (143), `sankey-server.ts` (174), `key-indicator-server.ts` (226),
`regression-server.ts` (233), `plot-builder-server.ts` (377), `statistical-tests-server.ts` (392).

## Design

### 1. New render endpoint / branch
- Add a `render` request path that takes: `projectUid`, `envId`, `datasetFileId`,
  `datasetFilters`, `kind` (enum of the 9), `spec` (dict) — and **no `code`**.
- Gate: keep `project-summary:read` (viewer) — legitimate, since the server now
  controls the code.
- On the existing `/execute`, **reject `purpose="render"`** (or drop the value from
  the enum) so the old client path can't smuggle code. Any run carrying free-form
  `code` requires a real `:execute` permission as today.

### 2. Server-side render registry
- New module `app/services/execution/render/` with one builder per kind:
  `RENDER_BUILDERS: dict[str, Callable[[spec], str]]`. Each returns
  `preamble(injection) + _XXX_PY + call(spec)`. The `_XXX_PY` bodies are ported
  verbatim from the `*-server.ts` `String.raw` blocks (they're already pure Python).
- Each builder validates its spec (pydantic model per kind): column names must be
  strings, enums constrained, numbers bounded. Reject unknown keys.

### 3. Spec schema per kind (from the builders' current spec objects)
- table1: `{ selected:[{name,numeric}], group:str|null, metrics:[enum] }`
- kaplan-meier: `{ time, event, group?, confidenceLevel:float }`
- (correlation-matrix, plot-builder, regression, statistical-tests, sankey,
  key-indicator, map): same treatment — capture the current builder's `spec` object
  as a pydantic model. Exact fields confirmed from each `build*Code` signature.

### 4. Frontend
- Each component stops building `serverCode`; instead sends `{kind, spec}` via a new
  `renderOnServer(kind, spec, {datasetFileId, datasetFilters})`.
- Delete the `_XXX_PY` blocks from the `*-server.ts` files (now server-owned). Keep
  the spec-building logic (column-id→name resolution) client-side.
- Parity is the acceptance test (see below): same rendered output as today.

### 5. WASM / front-only mode
- Front-only mode still runs the analysis in-browser (its own path, not `/execute`).
  The `_XXX_PY` is only the server path — confirm the browser path is independent so
  removing the server builders' PY doesn't touch front-only. (It is: components
  compute in JS/pyodide for front-only; `-server.ts` is the server path only.)

## Migration order (per component, independently shippable)

Do it one analysis at a time — each is a self-contained slice with its own parity
test, so it can land and be verified before the next.
1. **table1** (111 lines, simplest spec) — establishes the registry + endpoint + the
   parity-test harness.
2. correlation-matrix, map, kaplan-meier (small).
3. sankey, key-indicator, regression.
4. plot-builder, statistical-tests (largest).
Once all 9 are migrated, remove `purpose="render"` from the `/execute` enum.

## Verification (per component)

Parity test = the crux. For each kind, on a fixed dataset + spec:
- Old path (client-built code via `/execute`) vs new path (server-built from spec)
  must produce **byte-identical** `stdout`/`table`/`figures`/`html`.
- Add a backend test feeding a known spec → asserting the emitted JSON shape.
- Security regression test: a viewer POST with `purpose="render"` + free-form `code`
  → 403/400 (no execution); a viewer render via `{kind, spec}` → 200.

## Effort estimate

- Endpoint + registry + spec models + parity harness: ~1 slice of setup (table1).
- Each remaining component: port its `_XXX_PY` + spec model + wire the component +
  parity test. Small ones ~½ day, plot-builder/statistical-tests ~1 day each.
- Total: a focused multi-day task, not a one-liner — but mechanical and low-risk
  because the Python already exists and parity tests catch any drift.

## Interim option (if the full migration slips)

A stopgap on `purpose="render"`: reject any submitted `code` that isn't an exact
match to a server-known generated program (hash allow-list) — reduces the surface
without the full port. Not chosen now; documented as a fallback.
