Linkr · backend full-stack

Où vit chaque donnée : base relationnelle vs fichiers bruts

Pour chaque entité, on croise trois sources : son stockage actuel en mode client-only (IndexedDB), ce que produit l'export ZIP, et ce qui existe déjà côté API. La règle : métadonnées légères en base, contenu lourd/binaire en fichiers sous un dossier racine unique, calqué sur linkr-portal/.

Base — métadonnées, relations, requêtes transversales Fichiers — contenu lourd, git-lisible, façon portal Recalculable — cache, peut ne pas être persisté

01Le principe de partage

La ligne est nette et confirmée par les deux explorations. Rien de nouveau à inventer : l'export ZIP fait déjà exactement cette séparation (un _tree.json de métadonnées + les fichiers de contenu à leur chemin). Le backend full-stack reproduit ce layout sur disque et indexe les métadonnées en base.

→ En base (SQLite / Postgres)

  • Identité & relations : id, workspaceId, projectUid, FK, cascades
  • Métadonnées : noms multilingues, description, config, status, badges, timestamps, auteur
  • Arbres de fichiers sans contenu (le _tree.json) : chemin, type, langage, ordre
  • Concept mappings (texte structuré), structure dashboards (tabs/widgets/filtres)
  • Registres : source-concept-id ranges & entries

→ En fichiers (data_dir)

  • Code & scripts : IDE, ETL, SQL, code inline des widgets, fichiers de plugins
  • Données : CSV/Parquet des datasets, fichier source brut des mappings, blobs Parquet
  • Fichiers de bases importées (vocabulaires OHDSI) — dédupliqués par hash
  • Markdown : README, pages wiki
  • Pièces jointes binaires : readme, wiki

03Où tourne le calcul : décision d'architecture

Décision structurante, actée. Elle vaut pour toute l'app (warehouse, datasets, IDE, dashboards), pas seulement le stockage. Deux modes de déploiement, deux endroits pour le calcul — et le mode seul décide, jamais la nature de la donnée.

Full-stack (CHU) — compute 100 % serveur

Cible des déploiements en établissement. DuckDB, R et Python s'exécutent sur le serveur ; le WASM n'est pas chargé. Le navigateur envoie du SQL / des specs d'analyse et ne reçoit que des résultats agrégés qu'il affiche.

  • Perf : postes hospitaliers peu puissants → le serveur mutualisé calcule, le poste reste léger.
  • Sécurité : la donnée patient brute ne descend jamais sur le poste (pas de cache, pas d'IDB, pas de RAM navigateur).

Front-only (WASM) — conservé

Déploiement statique (GitLab Pages, linkr-portal), démos, données publiques (MIMIC). C'est le seul mode où le compute est dans le navigateur, via DuckDB-WASM / Pyodide / WebR.

  • Pas de backend → le WASM navigateur reste le moteur, comme aujourd'hui.
  • N'est pas destiné à manipuler de la vraie donnée patient.
Pas de classification de sensibilité. On n'essaie jamais de trier « donnée sensible vs non sensible » (impraticable, une colonne OMOP à la fois). La frontière est technique : tout ce qui lit les tables s'exécute au serveur ; le navigateur ne fait que réafficher / re-trier des résultats déjà reçus. Le drapeau isServerMode() (présence de VITE_API_URL) tranche, rien d'autre.

C'est l'architecture standard du domaine : OHDSI/ATLAS (front génère le SQL, WebAPI l'exécute, analyses en R serveur — zéro donnée dans le navigateur), Dataiku (moteur central + SQL pushdown, kernels R/Python serveur), Metabase/Superset (pushdown + cache serveur, navigateur = rendu), Posit Workbench / JupyterHub (sessions R/Python isolées par utilisateur côté serveur). Aucun acteur sérieux en santé ne fait tourner le moteur analytique dans le navigateur.

  1. Séquençage (l'app reste utilisable à chaque étape). a — Stockage : métadonnées en base, blobs (dont lignes de dataset en Parquet) sur disque serveur. C'est le socle : sans lui le compute serveur n'a rien à lire.   b — Moteur DuckDB serveur : une API de requêtes remplace queryDataSource (~142 appels) et computeStats ; le navigateur reçoit des lignes de résultat.   c — R / Python serveur : exécution isolée par session (voir §06), en dernier car le plus délicat.
  2. Une option « tout serveur » à activer ? Non — elle tombe du mode. En mode serveur, queryDataSource route vers l'API ; il n'y a rien à « activer ». Pas de troisième mode à maintenir.

04Datasets en full-stack

Application concrète de §03 à l'entité Dataset. Le modèle actuel (client-only) charge toutes les lignes en RAM navigateur (_loadedData, double copie sérialisée pour le dirty-check) et injecte JSON.stringify(toutes_les_lignes) dans Pyodide/WebR. Sur un CSV de 100k lignes c'est des dizaines de Mo dans l'onglet — intenable et contraire à §03.

  1. Lecture seule pour les datasets importés. Un fichier importé est une donnée source, immuable — même principe que le warehouse OMOP (« source data never modified »). On affiche/trie/filtre/analyse côté serveur, on n'édite plus cellule par cellule. Toute transformation passe par le pipeline (qui produit une nouvelle sortie). Supprime d'un coup le problème des 100k lignes en RAM.
  2. Analyses = exécution serveur, résultat seul. Le code R/Python tourne là où le Parquet est local ; le navigateur reçoit la sortie rendue (table, figure, stdout/stderr), jamais les lignes. analysis-executor.ts devient un client d'API en mode serveur.
  3. Lignes en Parquet, pas en JSON. Le parser produit aujourd'hui des lignes keyées par columnId sérialisées en JSON. Pour paginer/agréger sans tout désérialiser, on écrit un .parquet (colonnaire). Dette signalée : ne PAS toucher au parsing d'import dans la tâche en cours ; à traiter avec le compute serveur des datasets.
  4. Point ouvert : petits datasets saisis à la main. Créer une grille vide et la remplir à la main reste un cas légitime (petits volumes). À traiter comme un mode d'édition explicite « petit dataset », séparé de la lecture seule des gros fichiers importés — non tranché, non bloquant.

05Le dossier racine « Application database »

Un seul dossier configurable (LINKR_DATA_DIR, déjà en place) contient tout : la base, les blobs, et l'arbo git-lisible. C'est le pendant serveur de linkr-portal/.

# LINKR_DATA_DIR (ex. /var/lib/linkr ou ~/.linkr) linkr-data/ ├─ linkr.db # base : métadonnées + relations (ou Postgres externe) ├─ workspaces/ │ └─ <ws-slug>/ │ ├─ workspace.json README.md │ ├─ projects/<p>/ # scripts/ datasets/ dashboards/ … │ ├─ wiki/ mapping-projects/ etl/ sql-scripts/ │ ├─ databases/ catalogs/ data-quality/ plugins/ │ └─ source-concept-ids/ └─ _files/ # blobs partagés dédupliqués par hash (Parquet, uploads) └─ <sha256>.parquet
Décision ouverte. Écrit-on toutes les métadonnées aussi en fichiers (arbo git complète, comme le portal), ou seulement les blobs — la base restant l'unique source de vérité des métadonnées ? Voir décision ①.

06Exécuter R et Python côté serveur

Conséquence de §03/§04 : les analyses (datasets, IDE, dashboards) doivent tourner sur le serveur. État actuel + pistes. Étape (c) du séquençage — la plus délicate, à faire en dernier.

Ce qui existe déjà

  • docker/Dockerfile.api installe déjà r-base → Rscript disponible dans l'image API. Python est l'interpréteur du backend.
  • app/services/execution/ existe mais est vide (juste __init__.py). Aucune dépendance R↔Python (pas de rpy2), aucun runner branché.
  • Côté navigateur : pyodide-engine.ts (Python) + webr-engine.ts (R) — restent le moteur du mode front-only uniquement.

À construire (piste)

  • Un service d'exécution serveur : Python via sous-process/venv, R via Rscript (pas besoin de rpy2 — on passe les données par fichier Parquet et on récupère la sortie).
  • Injection des données par le serveur : le Parquet du dataset est monté localement (Arrow/pandas côté Python, arrow/duckdb côté R) — plus de JSON.stringify des lignes.
  • Isolation par session (modèle Posit Workbench / JupyterHub) : process séparé, quotas CPU/mémoire, timeout, répertoire de travail jetable. Surface maîtrisée car infra CHU + utilisateurs authentifiés (pas un SaaS public).
  • Retour : uniquement le RuntimeOutput (table, figures encodées, stdout/stderr) — même contrat que l'executor actuel.
À trancher le moment venu. R et Python : deux runners séparés, ou un orchestrateur commun (mêmes endpoints POST /execute, param language) ?   Process direct vs conteneur par exécution (isolation forte mais lourde) ?   Réutilisation d'un kernel chaud entre exécutions (perf notebooks) vs cold-start propre à chaque run ? Aucune de ces questions ne bloque le stockage (étape a).

07Décisions à trancher avant de coder

  1. Fichiers : source de vérité ou export ? A — Base = vérité pour les métadonnées ; les fichiers ne stockent que les blobs ; l'arbo git complète est générée à la demande via l'export existant. Plus simple, pas de double écriture à synchroniser.   B — On écrit systématiquement l'arbo complète (façon portal) à chaque changement : git-lisible en continu, mais double source à garder synchro. Reco : A.
  2. Import de dataset — le chemin prioritaire. Remodeler dataset.py (aujourd'hui scaffold obsolète) en DatasetFile + DatasetAnalysis (base) ; le CSV/Parquet et le fichier original vont dans data_dir ; endpoints d'upload + parse. C'est la première brique concrète.
  3. Couche blobs + déduplication. Un service de stockage fichiers unique (écrit/lit sous data_dir/_files/<hash>), réutilisé par datasets, databases, attachments. Reproduit le contentHash + dedupRef du client.
  4. Caches : persister ou recalculer ? catalog_results, *_stats_cache, scores : reco ne pas les mettre en base — les recalculer côté serveur à la demande (ils sont volumineux et dérivés).
  5. Réglage UI du dossier racine. Aujourd'hui LINKR_DATA_DIR est fixé côté serveur (lecture seule dans le wizard). Confirmer qu'on reste là-dessus (recommandé, sécurité) plutôt qu'un chemin choisi depuis le navigateur.
