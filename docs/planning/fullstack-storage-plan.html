Linkr · backend full-stack

Où vit chaque donnée : base relationnelle vs fichiers bruts

Pour chaque entité, on croise trois sources : son stockage actuel en mode client-only (IndexedDB), ce que produit l'export ZIP, et ce qui existe déjà côté API. La règle : métadonnées légères en base, contenu lourd/binaire en fichiers sous un dossier racine unique, calqué sur linkr-portal/.

Base — métadonnées, relations, requêtes transversales Fichiers — contenu lourd, git-lisible, façon portal Recalculable — cache, peut ne pas être persisté

01Le principe de partage

La ligne est nette et confirmée par les deux explorations. Rien de nouveau à inventer : l'export ZIP fait déjà exactement cette séparation (un _tree.json de métadonnées + les fichiers de contenu à leur chemin). Le backend full-stack reproduit ce layout sur disque et indexe les métadonnées en base.

→ En base (SQLite / Postgres)

  • Identité & relations : id, workspaceId, projectUid, FK, cascades
  • Métadonnées : noms multilingues, description, config, status, badges, timestamps, auteur
  • Arbres de fichiers sans contenu (le _tree.json) : chemin, type, langage, ordre
  • Concept mappings (texte structuré), structure dashboards (tabs/widgets/filtres)
  • Registres : source-concept-id ranges & entries

→ En fichiers (data_dir)

  • Code & scripts : IDE, ETL, SQL, code inline des widgets, fichiers de plugins
  • Données : CSV/Parquet des datasets, fichier source brut des mappings, blobs Parquet
  • Fichiers de bases importées (vocabulaires OHDSI) — dédupliqués par hash
  • Markdown : README, pages wiki
  • Pièces jointes binaires : readme, wiki

03Le dossier racine « Application database »

Un seul dossier configurable (LINKR_DATA_DIR, déjà en place) contient tout : la base, les blobs, et l'arbo git-lisible. C'est le pendant serveur de linkr-portal/.

# LINKR_DATA_DIR (ex. /var/lib/linkr ou ~/.linkr) linkr-data/ ├─ linkr.db # base : métadonnées + relations (ou Postgres externe) ├─ workspaces/ │ └─ <ws-slug>/ │ ├─ workspace.json README.md │ ├─ projects/<p>/ # scripts/ datasets/ dashboards/ … │ ├─ wiki/ mapping-projects/ etl/ sql-scripts/ │ ├─ databases/ catalogs/ data-quality/ plugins/ │ └─ source-concept-ids/ └─ _files/ # blobs partagés dédupliqués par hash (Parquet, uploads) └─ <sha256>.parquet
Décision ouverte. Écrit-on toutes les métadonnées aussi en fichiers (arbo git complète, comme le portal), ou seulement les blobs — la base restant l'unique source de vérité des métadonnées ? Voir décision ①.

04Décisions à trancher avant de coder

  1. Fichiers : source de vérité ou export ? A — Base = vérité pour les métadonnées ; les fichiers ne stockent que les blobs ; l'arbo git complète est générée à la demande via l'export existant. Plus simple, pas de double écriture à synchroniser.   B — On écrit systématiquement l'arbo complète (façon portal) à chaque changement : git-lisible en continu, mais double source à garder synchro. Reco : A.
  2. Import de dataset — le chemin prioritaire. Remodeler dataset.py (aujourd'hui scaffold obsolète) en DatasetFile + DatasetAnalysis (base) ; le CSV/Parquet et le fichier original vont dans data_dir ; endpoints d'upload + parse. C'est la première brique concrète.
  3. Couche blobs + déduplication. Un service de stockage fichiers unique (écrit/lit sous data_dir/_files/<hash>), réutilisé par datasets, databases, attachments. Reproduit le contentHash + dedupRef du client.
  4. Caches : persister ou recalculer ? catalog_results, *_stats_cache, scores : reco ne pas les mettre en base — les recalculer côté serveur à la demande (ils sont volumineux et dérivés).
  5. Réglage UI du dossier racine. Aujourd'hui LINKR_DATA_DIR est fixé côté serveur (lecture seule dans le wizard). Confirmer qu'on reste là-dessus (recommandé, sécurité) plutôt qu'un chemin choisi depuis le navigateur.
